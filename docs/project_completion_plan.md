## 목표

사용자가 내부 JSON/YAML을 직접 다루지 않고 GUI에서 지식·제품·정책을 관리하고,
저장한 NVMe Identify 응답을 검사할 수 있는 로컬 Windows 도구를 완성한다.
검사는 선택한 Bundle·제품 Profile·Context·정책·지식 리비전에 대해 재현 가능해야 한다.
실제 SSD 명령 실행은 저장 로그 기반 v1이 완성된 뒤 별도 단계로 진행한다.

설계 원본은 ssd_nvme_validation_system_design.md다. 이 문서는 실행 순서와 완료 기준이며
구현 완료를 주장하는 문서가 아니다. SQLite 전환의 현재 계약은 sqlite_transition.md를 따른다.

## 현재 상태

- Builder, 정규화, resolve/evaluate, 출처 추적, 후보 Bundle 비교 구현.
- Base 2.0e + NVM 1.0e, Base 2.1 + NVM 1.1 후보 데이터 보유.
- id-ctrl 텍스트 로그 GUI 입력과 공통 Actual, 초기 6개 규칙과 5단계 후보 확대 연결.
- SQLite 원본 리비전, 규칙/정책 편집, 검사 이력·과거 리비전 재실행 구현.
- 회귀 기록은 상단 단계별 실행 기록과 current_status.md를 따른다.
- 첨부 로그의 기록된 결과: 6개 규칙 PASS, 필드 PASS 5 / REVIEW 61 / UNKNOWN 3.
- DB는 원본 JSON/YAML과 관리 검색 인덱스를 보존하며 Bundle·문서·실행 필드·규칙·매핑 폼을 제공한다.
  전체 PDF 구조의 모든 필드를 관계형 테이블로 분해한 상태는 아니다.
- id-ctrl/id-ns 저장 입력 묶음 구현. Namespace 규칙 확대는 candidate/TEST로 검증했으며 실제 추가 로그 형식 확인은 대기 중이다.
- Product Profile 명시적 선택·후보 제안·등록 FW 비교 구현. 실제 제품 Profile/FW 자료는 미확보.
- NVMe 및 OCP2.6 focused candidate 규칙을 등록했다. 전체 규격과 실제 제품 적용은 미완성이고 MFND는 제외다.

## 공통 실행 계약

모든 단계의 프롬프트는 이 계약을 참조한다.

1. 기존 Builder, Actual 정규화, Resolver, 출처 추적과 검사 재현성을 재사용한다.
2. SQLite가 실제 원본이다. legacy 파일과 DB를 두 개의 수정 가능한 원본으로 만들지 않는다.
3. 원본 DB와 과거 검사 이력을 보존한다. 스키마 변경 전에 백업·복원 경로를 확보한다.
4. generated/는 직접 편집하지 않는다. 기존 미커밋 작업을 삭제·초기화하지 않는다.
5. 규격 값과 실제 제품/내부 정책은 원문 또는 명시적으로 입력한 자료에서만 등록한다.
   미확인은 UNKNOWN, 추출 지식은 candidate, 개발 가정은 provisional로 남긴다.
6. experimental 후보 실행은 유지한다. confirmed 승격에는 검토자와 검토 근거가 필요하다.
7. Reserved를 expected=0으로 바꾸지 않는다. 조건 누락과 타입 오류를 0/false로 바꾸지 않는다.
8. 지원 비트를 검사하는 정책과 그 비트에 종속된 Actual 일관성 검사를 독립적으로 유지한다.
9. 충돌을 덮어쓰기나 암묵적 우선순위로 해결하지 않는다. 기존 명시적 override 계약을 유지한다.
10. 각 단계는 의미 있는 테스트와 완료 기준을 확인하고 문서의 현재 상태를 갱신한다.
    다음 단계 기능은 선행 필요가 있을 때만 최소한으로 추가한다.
11. 자료가 없는 실제 요구사항은 합성 TEST/FIXTURE와 구분하고 작업 목록에 남긴다.
    그 자료와 무관한 구현/테스트는 계속한다. 정보 부재를 실제 규칙 완성으로 표시하지 않는다.

|---|---|---|

7–8의 개발은 진행할 수 있다. 실제 OCP/MFND 적합성 범위는 자료 확보 전 미완료로 표시한다.

## 1. 기준선과 DB 보호

목적: 현재 동작을 안정적인 기준으로 고정한다. 대규모 리팩터링이나 새 규칙 추가를 하지 않는다.

완료 기준:
- 기존 기능·설계 설명의 불일치와 남은 범위를 기록한다.
- 기존 id-ctrl 결과를 재현하고 전체 회귀 테스트를 실행한다.
- 원본 수정과 검사 이력을 포함한 DB 백업/복원, 버전 확인, 스키마 마이그레이션 계약을 검증한다.
- 백업 시점·DB 연결 상태를 고려한 안전한 백업 경로를 제공한다.
- 잘못된 가져오기/리비전 충돌/검증 실패는 저장 내용을 변경하지 않는다.

복사할 프롬프트:

```text
docs/project_completion_plan.md의 공통 실행 계약을 지키며 1단계를 구현해줘.
현재 코드·문서·SQLite를 점검해 구현 사실과 미완성을 구분하고, 범위를 저장 로그 기반 v1으로 고정해줘.
기존 Builder·정규화·Resolver와 현재 로그 결과를 유지해줘. DB 스키마 버전 확인, 안전한 백업·복원,
마이그레이션 절차와 실패 시 원본/검사 이력 보존을 구현·검증해줘.
첨부 id-ctrl 로그와 전체 회귀 테스트로 기준선을 확인하고, 문서의 오래된 설명을 현재 구현에 맞춰 정리해줘.
이번 단계에서 실제 SSD 명령이나 새 제품 정책을 추가하지 말고 완료 기준·검증 결과·남은 문제를 보고해줘.
```

## 2. 내부 파일을 몰라도 쓰는 지식 관리

목적: SQLite 도입의 관리 편의 효과를 GUI에서 완성한다.

완료 기준:
- Bundle 등록은 데이터에서 읽으며 두 Bundle을 코드 분기로 고정하지 않는다.
- 규격 문서/버전/원문 위치, 필요한 필드와 비트/배열, 규칙, Capability 매핑을 조회·편집한다.
- 단순 조건과 필드 비교는 폼으로 입력한다. 복잡한 조건의 고급 입력은 별도로 둔다.
- 변경 사유/미리보기/참조 무결성/동시 편집 충돌/되돌리기 이력을 제공한다.
- 출처 수정과 규칙의 적용 Bundle 변경을 구분하며 candidate 검토와 confirmed 근거를 관리한다.
- DB 정규화는 편집·조회에 필요한 부분부터 한다. 전체 구조 재추출이나 엔진 재작성은 선행하지 않는다.

```text
docs/project_completion_plan.md의 공통 실행 계약을 지키며 2단계를 구현해줘.
현재 SQLite 원본과 리비전을 유지하면서 Bundle·규격 문서·필드/비트/배열·규칙·Capability 매핑을
GUI에서 검색하고 폼으로 관리할 수 있게 해줘. Bundle 등록/선택은 DB 데이터 기반으로 바꿔줘.
단순 적용 조건과 필드 관계는 사람이 읽는 입력 폼을 제공하고 내부 JSON은 고급 화면으로 옮겨줘.
필요한 관리 데이터부터 DB 모델/조회 계층을 정리하되 기존 Builder·Resolver를 재사용하고
원본/인덱스 이중 편집을 만들지 말아줘. 변경 미리보기, 참조 검증, 검토 근거, 리비전 충돌,
새 리비전으로 되돌리기를 구현해줘. 기존 데이터 마이그레이션과 과거 검사 재현성을 테스트해줘.
```

## 3. 복수 명령의 저장 응답과 공통 Actual

목적: 하나의 DUT 검사에 Controller/Namespace의 여러 응답을 연결한다.

완료 기준:
- 우선 id-ctrl/id-ns 텍스트 로그를 통합한다. raw/JSON은 기존 정규화 계층을 연결한다.
- NVM 전용 Identify Controller/Namespace 등 추가 응답은 실제 파일/확인된 형식부터 등록한다.

- 서로 다른 DUT/Namespace/수집 세션을 자동 병합하지 않는다.
- 인덱스/배열과 namespace별 값을 구분하고 원문 표현과 파일 해시를 보존한다.
- 최신 도구의 추가 필드는 보존한다. 목표 Bundle에서 미정의인 필드를 자동 오류/zero로 만들지 않는다.
- 실제 추가 로그가 없으면 합성 fixture로 입력 경로를 검증하고 실제 형식 확인을 남긴다.

## 4. 제품 Profile, FW, Context와 정책

목적: 제품 차이를 코드 조건문 대신 관리 가능한 데이터로 표현한다.

완료 기준:
- 제품 Profile은 Bundle 바인딩, 정책, Capability 요구, 적용 조건으로 구성한다.
- 먼저 명시적 선택을 완성하고 자동 선택은 제안/확인 방식으로 추가한다.
- 0개 후보는 UNKNOWN, 복수 후보는 모호성으로 표시하며 임의 선택하지 않는다.
- FW 비교 규칙은 제품별로 명시한다. 정의되지 않은 FW 문자열을 숫자/사전순으로 추정하지 않는다.
- 로그에서 관찰한 사실, 사용자 Context, 가정, 정책 요구를 구분한다.
- Profile 수정 전후와 Namespace별 Context를 검사 이력에 보존한다.

```text

우선 사용자가 제품 Profile을 명시적으로 선택해 같은 Actual을 검사하는 경로를 완성하고,

FW 비교는 제품별로 등록된 비교 방식만 사용하고 정의가 없으면 UNKNOWN으로 처리해줘.
```
