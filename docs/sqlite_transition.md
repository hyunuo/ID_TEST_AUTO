# SQLite 원본 저장소 전환

## 승인된 방향과 실행 계획

2026-10-11 사용자 승인: SQLite를 규칙·정책의 원본 저장소로 사용하고 GUI에서 관리한다.
기존 Builder, 정규화, Resolver와 candidate/UNKNOWN/충돌 처리는 유지한다.

1. 버전이 있는 SQLite 저장소를 추가한다. 기존 knowledge/와 candidates/는 최초 가져오기 자료다.
2. 원문 데이터와 출처를 손실 없이 보존한다. 수정은 변경 사유와 이전 리비전을 요구하며
   변경 전후를 모두 보존한다. 생성물은 원본으로 가져오지 않는다.
3. DB 리비전을 기존 Builder 입력 형식으로 일시적으로 투영해 기존 엔진을 재사용한다.
   이 파일은 원본이 아니며 사용자 관리 대상이 아니다.
4. GUI에 Bundle별 규칙·정책 목록, 편집, 원본 내보내기/가져오기와 검사 이력을 연결한다.
5. 검사 입력 원문, Context/정책 선택, 리비전, 전체 결과를 저장해 과거 결과를 보존하고
   같은 리비전으로 재실행할 수 있게 한다.
6. 기존 로그 결과와 DB 경로의 동등성, 입력 검증, 동시 수정 충돌, 이력 보존을 테스트한다.

## 저장 계약

- 로컬 DB: `data/validator.sqlite3`. generated/에 두지 않는다. 삭제해도 되는 캐시가 아니다.
- source_blob + revision_source: SHA-256으로 식별하는 원본 내용과 리비전별 논리 경로.
- revision: 불변 리비전, 부모 리비전, 변경 사유, 저장 시간.
- rule_index: Bundle/필드/규칙/정책/근거 조회용 인덱스. 원본과 같은 트랜잭션에서 생성한다.
- validation_run: 원본 로그와 선택 옵션, 사용 리비전, 전체 결과. 과거 결과는 수정하지 않는다.
- 최신 리비전만 검사에 자동 사용한다. 편집은 expected_revision을 요구하며 오래된 편집은 거절한다.
- 초기 자료가 변경되어도 이미 생성한 DB에 자동 덮어쓰지 않는다. 명시적으로 가져와 검증한다.
- candidate는 candidate로, 가정 정책은 provisional로 유지한다. 승인 상태를 임의 승격하지 않는다.
- 백업/이동용 내보내기는 전체 원본을 포함한 버전 JSON이다. 원본 PDF는 외부 원문으로 유지한다.
- 검사 이력까지 포함한 전체 DB 백업·검증 후 복원을 제공한다. 스키마 v2와 v1 migration,
  사전 백업, 실패 rollback, 복원 후 편집 충돌 계약은 [DB 운영 안내](database_operations.md)를 따른다.

## 이번 단계의 범위

현재 두 Bundle과 id-ctrl 파일럿 데이터의 관리 및 검사에 먼저 적용한다.
GUI는 기존 규칙의 대상/제약/조건/근거 편집과 규칙 추가·삭제를 지원한다.
전체 원본은 고급 가져오기/내보내기로 관리한다. 전체 Identify 규칙 완료나 실제 DUT 적합성
검증 완료를 의미하지 않는다. 실제 SSD 명령 실행, Excel, 제품 정책 자동 추정은 추가하지 않는다.

## 완료 및 검증

위 1–6단계를 현재 파일럿 범위에 구현했다. SQLite의 원본 문서와 조회 인덱스는 동일
트랜잭션에서 저장되며 파일 기반 엔진과 DB 경로의 판정 동등성을 확인했다.
규칙 수정, 정책 변경, 추가·삭제, 오래된 수정 거절, 원본 교환, 누락 조건, 충돌 보존,
미검토 상태 유지, 세션 보호와 검사 이력·재실행을 테스트한다.
전체 회귀 366개 통과. 첨부 id-ctrl 로그의 기본 선택 결과는 6개 규칙 PASS,
필드 PASS 5 / REVIEW 61 / UNKNOWN 3으로 기존 결과와 같다.

관리 GUI의 폼은 실행 규칙/정책을 대상으로 한다. 구조·필드·Capability 매핑의 개별
편집 화면은 아직 없으며 전체 원본 패키지에서 수정 후 검증하여 가져온다.
불변 리비전에서 이전 자료를 내보내 다시 가져오면 복원도 새 리비전으로 남긴다.
DB 원본 내용은 JSON/YAML 문서를 보존하는 방식이며, 전체 필드 구조를 관계형 테이블로
분해하는 대규모 재설계는 수행하지 않았다.
